# 型: 欠陥の目的化 (Defect as Purpose)

## 確度

**B** — 自プロジェクト実験(RQ01b)で支持。integrated 条件で最も punchline スコアが高い台本がこの型を使った。

## 型の説明

欠陥・制約・失敗を「実は目的だった」と言い切ることで、それまでの意味を逆転させる。

```text
欠陥(ネガティブ) → 目的(ポジティブ)への再解釈 → 全意味の反転
```

## 典型的な構造

1. 欠陥を積み上げる(エスカレーション)
2. 観客は「それはまずい」と思っている
3. 欠陥が実は意図された目的だったと宣言する
4. すべての欠陥が一つの解釈に回収される

## 実例

- RQ01b integrated-py: 「動いてます。インデントが正しいので」(インデントが仕様=目的)
- RQ01b integrated-js: 「動かないところが、明日の仕事です」(バグが仕事の源=目的)
- RQ01: 「Javaを使うためのJavaだよ」(Javaの複雑さが目的)

## 対応 MicroSkill

- callback(過去の欠陥を回収)
- escalation(欠陥の積み上げ)
- deadpan(平然と宣言)

## 証拠

- RQ01b integrated-php: 最高 punchline 6/7。「動いてますから」が全欠陥を回収
- RQ01b integrated-py: punchline 6/7。「インデントが正しいので」で全話が回収される
- 欠陥の目的化を含む integrated 台本は baseline より punchline +2.3

## 反例・限界

- 目的化の宣言が冗長だと explained_joke になる。宣言は一行で、それまでの台本に暗黙に準備されていなければならない
- 目的化の前に欠陥の積み上げ(エスカレーション)がないと、反転の重みが出ない

## 次に測ること

- 「欠陥の積み上げ数」と「目的化の効き」の関係
- 目的化を説明する行の削除テスト(Explanation Test)
